# ugc-lens 架构设计

> 版本：v0.1 草案。实现过程中有变化，先改这份文档再改代码。

## 1. 定位

ugc-lens 是一个**分析用户互动内容（评论、弹幕、回复等）的轻量 Agent**，以 npm 包发布。核心不依赖任何界面，图形界面作为可选入口后续提供（见第 2.1 节）。

发布第一版之后扩展为**通用文本记录**分析：商品评价、问卷开放题、客服工单、访谈记录等，只要是“一条文本加一些元数据”的数据都能分析（roadmap 第 9.5、14 步）。分块、去重、关键词、高峰检测这些算法本来就和平台无关，需要改的是统一格式里的类型、CSV 导入和提示词。

- 输入：JSON、JSONL/NDJSON、CSV/TSV、TXT、Markdown 和日志文本。结构化文件字段由模型识别，纯文本使用内置映射；通用记录用 record 类型，不假设来自社媒平台（第 5 节）。
- 输出：带证据引用的分析报告（Markdown / 单文件 HTML），以及可追问的结论。
- 使用方式：命令行、代码调用、MCP 服务（供 Claude Code、Codex 等宿主 Agent 调用）。

不做的事：
- 不做数据搜集（第二版通过数据源接口接入外部搜集工具）。
- 不做通用研究 Agent，不做多 Agent 协作。
- 不做以数字为主的表格分析（如 LIDA 那样让模型写代码计算、画图）。那是另一条路线，和以文本为主的流水线是两套东西。
- 不绑定任何一个数据来源或模型厂商。

## 2. 总体分层

```
┌──────────────────────────────────────────────────────┐
│ 入口层   CLI (对话 / watch / analyze / ask)   MCP 服务   代码 API │
└──────────────┬───────────────────────────┬───────────┘
               │                           │
     ┌─────────▼─────────┐       ┌─────────▼─────────┐
     │  分析流水线 (固定步骤) │       │  Agent 循环 (ask)   │
     │  解析→统计→分块总结→  │       │  模型自己决定调用哪些工具 │
     │  合并→引用校验→写报告  │       └─────────┬─────────┘
     └─────────┬─────────┘                 │
               │        ┌──────────────────▼──┐
               └───────►│  工具层 (function call) │
                        └──────────┬──────────┘
          ┌────────────────────────┼───────────────────────┐
   ┌──────▼──────┐        ┌────────▼───────┐       ┌───────▼───────┐
   │ 数据导入       │        │ 模型客户端         │       │ 本地存储          │
   │ 模型识别结构   │        │ OpenAI 兼容接口    │       │ 任务状态 / 报告     │
   │ 代码按规则转换 │        │ (见 providers.md)  │       │ playbook /     │
   │ 规则缓存       │        │                  │       │ learnings      │
   └─────────────┘        └────────────────┘       └───────────────┘
```

两条执行路径共享同一套工具层：

| 路径 | 什么时候用 | 谁决定下一步 |
|---|---|---|
| 分析流水线 | 新数据文件到达、`analyze` 命令 | 代码（步骤固定） |
| Agent 循环 | `ask` 追问、MCP 调用、第二版研究循环 | 模型 |

原则：**能用固定步骤完成的不交给模型决定**。只有需要根据中间结果选择下一步的场景才用 Agent 循环。

### 2.1 图形界面（可选，roadmap 第 19 步）

- 核心包不包含任何界面代码。命令行、MCP、图形界面都只是入口层，调用同一套代码 API。
- 图形界面优先做成本地 Web 页面：`ugc-lens ui` 启动一个本地 HTTP 服务并打开浏览器，不引入 Electron。
- 为了让界面以后能直接接入，核心从第一版起就要提供两样东西：
  1. **运行事件流**（第 3.5 节）：界面靠它显示进度，命令行也用它打印进度。
  2. **只读的状态与报告接口**：任务列表、报告、数据集统计都能通过代码 API 查询，不需要界面去读内部文件。
- 第一阶段（已实现）：`src/ui/server.ts` 用 `node:http` 提供接口，`ui/` 下是随包发布的静态前端（React + Animate UI + Tailwind CSS + Motion；源码位于 `web/`，Vite 构建至 `ui/`，前端依赖仅用于开发构建；SVG 图表与白名单 Markdown 渲染保留本地计算）。页面包括概况（数量、弹幕密度与高峰、发布时间、IP 属地、关键词、高赞内容、宿主模式的情感/主题/商业机会结果）、原文检索、报告阅读（`[ID]` 点开原文与回复链）。对话与一键分析属于第二阶段，需要模型配置。
- 安全边界：只监听 127.0.0.1；接口要求启动时生成的令牌（放在网址 `#` 片段，前端读取后存入 sessionStorage 并移出地址栏），比较用常量时间；检查 Host 为本机端口以防 DNS 重绑定，带 Origin 时必须同源；只读启动目录内的文件和用户主动选中的文件，按真实路径判断，符号链接指向目录外同样拒绝；响应带严格内容安全策略（脚本只允许同源、不允许内联脚本；样式允许内联以支持 Animate UI 的运行时样式与动画）。
- 选择文件：服务和浏览器在同一台机器上，“选择文件”由服务弹出系统文件对话框（macOS `osascript`、Windows PowerShell `OpenFileDialog`、Linux `zenity`/`kdialog`，`execFile` 不经 shell），拿到真实路径，宿主模式在数据目录或启动目录下的标注结果也能对上。弹不出时（无图形环境、经 SSH 转发访问）返回 501，界面改用浏览器文件选择或拖放，内容上传到 `~/.ugc-lens/ui/uploads/<内容哈希>/`（上限 512 MB，文件名只保留最后一段）。选中过的文件记入全局 `~/.ugc-lens/ui/recent.json`（最多 20 个，权限 600），重启后仍可直接打开；不写入启动目录。
- 打开文件复用 `loadDataset`：内置或缓存规则命中时不需要模型；否则按需读取模型配置识别结构，配置缺失返回可读错误。数据集只保存在服务进程内存中，页面记住上次打开的文件并在刷新后重新打开。

### 2.2 命令行与发布

- 命令行：直接运行 `ugc-lens` 进入持续对话（第 11 步），模型根据自然语言选择工具；`ugc-lens init`（交互式初始化：选提供商、列出 /models 选模型、填 key、发一次测试调用，写入全局配置）、`ugc-lens analyze <文件>`（生成报告）、`ugc-lens ask <文件> <问题> [追问...]`（追问，回答带 ID）、`ugc-lens watch <目录>`（监听目录，第 6.7 节）。结果打印到标准输出，进度打印到标准错误，可以直接重定向到文件。
- 配置从进程环境变量、当前目录的 `.ugc-lens/config.json`（不含密钥）、全局 `~/.ugc-lens/config.json` 读取（优先级从高到低，见 [providers.md](providers.md) 第 4 节）。任务状态和报告仍写在当前目录的 `.ugc-lens/` 下，只有模型配置进全局目录。
- 代码 API：`src/index.ts` 导出 `loadDataset`、`analyzeDataset`、`askDataset`、`watchDirectory`、`openTaskStore`、模型客户端和配置读取等，命令行和 MCP 复用这些核心能力。
- 发布：开发时直接运行 `.ts`；发布前用 `tsc -p tsconfig.build.json` 把 `src/` 编译到 `dist/`（含类型声明），因为 Node 不对 `node_modules` 里的 `.ts` 做类型剥离。包里只放 `dist/`、README、LICENSE。
- CI（GitHub Actions）：`ci.yml` 在每次推送和 PR 时跑类型检查、测试、编译，并把 `npm pack` 的包装到临时目录里运行 `--help`。`release.yml` 在 master 上 `package.json` 的版本号和 npm 上的不同时发布，用 npm Trusted Publishing（OIDC，不存 token），然后打 `v版本号` 标签。

### 2.3 默认交互对话（roadmap 第 11 步）

- `ugc-lens` 无参数时在终端进入持续对话，保留会话内历史；显式 `--help` 查看用法，原有 `init`、`ask`、`analyze`、`watch` 子命令继续提供。非交互输入无参数时仍打印帮助。
- `src/chat/session.ts` 提供会话核心，复用 `runAgent`；system prompt 在会话内固定，只有真实用户输入成为 user 消息。查询直接使用已有数据工具，避免嵌套一层问答 Agent。
- 会话工具：列出目录、导入支持的结构化文件和文本、查询数据、生成报告、启动/停止监听、查看监听任务。路径相对会话启动目录解析；只在需要文件位置或目标不明确时询问用户，不要求用户选择子命令。
- 导入后的数据集保留在内存，后续可以直接追问；生成报告复用固定流水线，输出保存路径和报告内容，不让模型编造执行结果。
- 监听使用独立的会话级取消信号，在后台运行，启动成功后工具立即返回，用户可以继续对话。一次会话只启用一个监听；停止或退出时取消并等待资源清理。任务按监听目录隔离持久化，完成和失败消息显示在终端，状态可由工具读取。
- `src/cli/chat.ts` 负责输入输出；`/exit`、`/quit`、Ctrl+D 或 Ctrl+C 退出并清理监听，单轮请求失败后仍可继续输入。模型配置沿用现有优先级，缺配置时提示运行 `ugc-lens init`。

### 2.4 MCP 服务（roadmap 第 12 步）

- `ugc-lens mcp [--cwd <目录>]` 提供本地 stdio MCP 服务，由宿主启动和停止；不启动 HTTP 服务、不监听端口。标准输出仅用于 MCP 协议，诊断信息只写标准错误。
- 使用官方 TypeScript SDK 处理握手、协议校验、工具发现、请求取消与 stdio 传输，避免自行维护 JSON-RPC 协议。依赖固定精确版本；CLI 动态加载 MCP 入口，普通命令不提前加载 SDK。
- `src/mcp/server.ts` 创建独立服务实例；每个实例拥有数据集和追问历史，不与默认 CLI 对话共享内存。`--cwd` 决定配置、映射缓存、报告与相对输入路径的基准，不修改进程工作目录。
- 工具为 `load_dataset`、已有的四个数据查询工具、`analyze` 和 `ask`。数据查询复用 `createDataTools` 的 schema 和实现；`analyze` 调用固定流水线；`ask` 调用 `askDataset`，返回引用校验结果。提供 file 时自动导入，也可用 dataset_id 选择已导入的数据。
- 模型配置按需读取：握手、工具发现及空的数据集列表不需要 API key；只有导入、分析、追问时才创建模型客户端。配置仍沿用 providers.md 的优先级。
- `ask` 返回 conversation_id，后续传回同一 ID 延续上下文；不同会话分开保存，同一会话绑定同一数据集，并发写同一会话时返回可恢复的错误。
- 参数由现有 Zod 工具及 SDK 校验；业务错误返回 `isError: true` 的工具结果，协议错误由 SDK 处理。请求取消传递到底层 fetch、导入和流水线；断开、EOF 或信号退出时取消未完成请求并清理资源。
- 仓库内附 `skills/ugc-lens/SKILL.md`，随 npm 包发布，用于指导宿主选择查询或完整流水线；README 提供 Claude Code 与通用 stdio 配置。不会自动修改用户的宿主配置或安装技能。
- Agent Skills 分发（roadmap 第 17.5 步）：`skills/` 下每个目录是一个符合 agentskills.io 规范的技能，`name` 与目录名一致，可由 `npx skills add sansan-mei/ugc-lens` 从 GitHub 安装到 Claude Code、Codex、Cursor 等宿主，也随 npm 包发布。
  - `ugc-lens`：使用本包。先判断 MCP 是否已连接；未连接时可用命令行 `analyze`、`ask` 完成任务，注册 MCP 需用户确认；模型配置由用户自行运行 `ugc-lens init`。
  - `cited-feedback-analysis`：不依赖本包和模型 key 的轻量技能，由宿主模型阅读数据，`scripts/evidence.mjs`（Node 18+、无依赖、单文件）负责建立记录索引、正则计数和引用核验。它是独立副本，不从 `src/` 导入，避免安装技能时还要安装本包；TXT、Markdown、CSV/TSV、JSON 字符串数组的 `line_N` 编号与 `src/ingest/formats.ts` 保持一致，由测试对照。嵌套回复按同一文本字段展开并记录 `parent_id`；核验只证明 ID 存在与摘句逐字出现，不评价解读质量。适用规模为一次会话能读完的几千条短文本，更大数据、弹幕时间线和逐条分类仍引导到 ugc-lens。

### 2.5 模型接口与缓存优化（roadmap 第 18 步，可选，待实现）

- 2026-11-06 评估后，本节除用量观测外暂缓（理由见 roadmap 第 18 步）。已实现：汇总用量时，未返回缓存字段的调用记为未知次数（`src/llm/usage.ts`），报告显示“未知”或“至少 N（M 次调用未返回）”，不再把缺失值当成命中 0。
- 当前所有模型请求仍走 OpenAI 兼容 Chat Completions；仅统一读取部分提供商的缓存命中用量，没有原生 Claude Messages 或 OpenAI Responses 适配，也没有分析结果自动复用。本节是后续设计，不代表现有能力；第 2.6 节安全与证据完整性修复已先行完成。
- 在 `AgentModel` 后增加按提供商、接口、模型及实际 endpoint 选择的能力适配：保留 Chat Completions，增加 OpenAI Responses 和 Claude Messages。自定义网关允许明确配置能力，不能只凭模型名字推断协议或把官方能力套到中转服务。模型选择和订阅账号授权是不同问题，本步骤不自动导入 Codex/Claude Code 登录凭证。
- 分清调用边界：ugc-lens 内部分析与对话的模型请求由本项目优化；Codex/Claude Code 作为 MCP 宿主时，其外层模型缓存由宿主管理。本项目只稳定 MCP 工具定义、控制返回体并复用本地分析产物，不宣称能设置宿主的缓存 TTL 或读取其账单。
- 提供商提示词缓存复用 KV 前缀，仍然生成新答复。固定指令、工具 schema 和可复用材料稳定在前，问题与批次数据在后；不添加动态时间或随机正文。遵守第 8.2 节固定 system、既有消息不可修改及工具配对约定；画像更新不能改写当前运行前缀。适配器必须保留接口要求回传的 reasoning/thinking 状态，用独立传输状态表达，不伪装成用户消息，也不把它存进画像。
- 缓存配置按能力映射到路由 key、模式、断点和 TTL，默认使用提供商适用的标准策略；更长 TTL 和显式断点需支持矩阵及配置验证。最小长度、可用模式、读写计费按模型和接口核实，不写成所有提供商共用常量。不额外发预热或保活请求；并发批次的冷启动不保证命中，不通过重发请求制造漂亮命中率。
- 统计区分总输入、缓存读取、缓存写入、普通输入和输出；按提供商口径归一化，保留未知状态。Claude 总输入需合并普通输入、缓存创建和读取；命中输入仍占上下文及现有 token 预算，不能直接从输入总量扣掉。费用按可核实价格配置估算，未知价格不报“节省 0 元”或承诺固定折扣。
- 本地结果复用作为本步骤后半段：先覆盖分块总结和逐条情感/主题评估，不缓存整段自由对话或有写入副作用的工具。键包含项目/profile 隔离、数据内容及 ID 映射、阶段及筛选/主题标准、有效提示词/playbook/schema、提供商/endpoint/接口/模型和影响结果的参数；使用画像时加入实际读取的画像快照。只缓存校验成功的完整阶段单元，失败、截断、遗漏不标成功，部分任务仅复用成功单元并重试其余。记录来源时间、模型和版本，区分本地命中和远端命中，不把历史调用用量当成本轮新消耗。
- 本地缓存提供强制刷新、容量/过期清理与并发原子写入；缓存损坏按未命中处理。关闭本地复用不代表清除远端 KV 缓存，远端 TTL 和删除能力由平台决定。不得缓存密钥、完整请求头或为了缓存复制完整用户历史。
- 验收依靠本地 HTTP 模拟与假模型验证接口、前缀、工具配对、用量、失效和隔离；真实命中率只能在用户选择真实模型后观测，不能由模拟测试推断。

### 2.6 安全与证据完整性（roadmap 第 15.5 步）

2026-11-06 已实现并通过离线回归。依据为用户针对 `master@bfc96f0` 的审查摘要；详细外部审查文件不在本机，验收范围以路线图第 15.5 步的六项及本仓库测试为准。

- **端点与凭证共同解析**：记录最终端点及凭证来源，禁止不可信项目配置（含项目 `.env`）仅覆盖端点便携带全局或进程中的密钥。端点去除末尾斜杠后按完整地址比较，允许复用范围及可信显式绑定规则见 providers 第 4.1 节；项目自行声明信任不能作为授权依据。错误信息不得包含凭证。
- **证据身份贯穿阶段**：原文、字幕片段、评论及回复采用可回查的证据身份，至少保留数据集/内容作用域、来源 ID 与类型。查询、时间轴、分块及引用校验共享标识约定；显示引用与校验索引不能各自生成互不兼容的 ID。字幕独立于弹幕参与分析，传入模型的正文与时间信息可在测试中核对。
- **去重与回复关系分离**：相同证据的重复导入合并回复集合，不以正文相等删除其他内容下的证据。文本归一化或观点聚合保留成员来源与各自父子关系。压缩保留直接父 ID、根 ID 和内容归属；无法解析的指向显式标未知，不能通过删除称呼制造默认归属。
- **覆盖按阶段记录**：按证据类型记录源数据存在性、转换成功/失败、导入、去重、提交模型、分析成功及失败/跳过原因。源不可观测时标未知；已发送不等于分析成功。字幕不能套用评论条数作分母，字段路径命中不等于产生有效片段，报告不得用单个成功标志替代这些状态。
- **拒绝缓存有边界**：结构指纹不能把空样本的拒绝外推为同结构所有文件不支持；拒绝结论保留原因和适用范围。强制重新识别成功须使后续普通导入恢复，不能继续被旧拒绝条目覆盖。
- **任务共享用量账本**：为本项目发起的调用传递任务身份，按调用/阶段汇总外层与内层用量，避免子结果再次累加。已知值和未知值分开，失败/取消不能清空已消耗用量。共享预算在新增调用前检查，并发请求在开始时检查预算，已在途请求可完成；任务最多允许一次额外 Agent 收尾，画像学习没有预算豁免；token 软上限与费用硬上限分开，不能把外层循环预算称为整次任务总成本上限。MCP 宿主模型的消耗不在可观测范围。
- **验收以输入和数据关系为准**：先写离线失败回归，再逐项修复；断言正文真正进入模型、回复仍指向正确证据、阶段分母可核对、所有内部调用只入账一次。完成这一步后再推进接口、缓存和提示词优化，不引入额外 Agent。

实现约定：

- 字幕证据 ID 为 `<content_id>:transcript:<序号>`；`dataset/evidence.ts` 提供与互动内容统一的回查，时间轴、引用校验、总结摘句和报告使用同一规则，`get_feedback` 可读取字幕。字幕单独分块，不凭互动条数决定是否分析；仅字幕文件允许空互动集合。
- `report.transcripts` 记录映射路径、源状态、段数及转换失败数。覆盖表另列导入、计划、已提交、成功、失败和跳过；没有配置字幕映射且无片段时标未知，不将其等同于源中没有。时间轴按字幕起点与弹幕事件建窗，跨窗字幕显示在已有重叠窗口，不为长视频生成大量空窗。
- 有回复的串不做正文合并；无回复的同文组保留所有成员 ID 与原文，大组拆回可装块单元，避免来源保留后突破单块上限。引用保留原文称呼，回复行携带 `parent/root/content`，显式直接父 ID 优先于容器父 ID，低信息过滤保留其他回复所指向的父节点。
- 拒绝缓存增加源文件路径与解析数据的摘要，仅复用相同输入的拒绝。旧版没有摘要的拒绝不再泛化复用；成功重新识别清除同指纹拒绝规则。成功映射仍按结构复用。
- `agent/usage.ts` 用 `AsyncLocalStorage` 传播任务账本，不改变模型消息或 system。默认任务软预算 200000 token（第 17 步根据真实数据从 100000 上调：一次完整报告约 10 万～15 万 token）；`runAgent`、`askDataset`、`analyzeDataset` 的预算参数可设入口上限，`createSession` / `createMcpServer` 可传 `tokenBudget`，代码 API 可用 `withTask(work, budget)` 包住导入及后续分析。嵌套阶段仍可设置更小的局部限制，但不能扩大外层任务预算。
- 每轮对话、一次 MCP 工具调用、一次 CLI analyze/ask 命令各自定义任务边界；后台每个文件分析使用独立任务，不继承启动监听那一轮的账本。本地缓存命中不虚增模型调用；重试失败尝试标记用量未知，成功响应仅计一次。已知用量与未知请求的字符估算分开，后者参与软预算检查，不能当作实际账单。
- `task_usage` 返回调用明细与总量；旧 `usage` 继续表示本层响应用量，不能再作为整次任务总量。报告和 CLI 显示任务统计，MCP 通过 `structuredContent.task_usage` 返回，错误对象携带当前快照，后台失败或取消时也保存到账本字段。缺失接口用量保持未知，不包含 MCP 宿主自身消耗。

### 2.7 联网搜索与网页读取（roadmap 第 16 步）

- **用途**：核实评论中的事实性说法，解释梗和圈内用语，补充内容与事件背景。外部资料只用于解释和核实，不替代数据证据，不进入统计分母。
- **入口范围**：默认关闭。对话与 `ask` 使用 `--web` 或配置 `web.enabled: true` 开启；固定 `analyze` 流水线不联网，保持报告可复现。MCP 服务需 `ugc-lens mcp --web` 开启，且只供服务内部的 `ask` 使用，不向宿主直接暴露 `web_search` / `web_fetch`：宿主通常自带联网能力，重复提供会多一条注入路径。
- **配置**（`src/web/config.ts`）：配置文件 `web` 字段与 `llm` 并列。开启联网只认参数（`--web`）、进程环境 `UGC_LENS_WEB` 和全局配置 `web.enabled`，项目配置及项目 `.env` 不能替用户开启，因为开启后数据内容可能经搜索词或 URL 发往外部。其他字段为 `provider`（`searxng` / `tavily`）、`base_url`、`api_key_env`、`api_key`、`max_calls`、`timeout_ms`、`max_bytes`、`max_chars`、`cache_ttl_hours`。优先级同模型配置：参数 > 环境变量（`UGC_LENS_WEB_PROVIDER`、`UGC_LENS_WEB_BASE_URL`）> 项目配置 > 全局配置 > 预设。来自全局配置或进程环境的 key 只能用于可信来源确定的端点，项目配置及项目 `.env` 改端点时不能带走它们，规则与第 2.6 节一致。
- **搜索后端**（`src/web/search.ts`）：SearXNG 调用 `GET <base>/search?format=json`，Tavily 调用 `POST <base>/search`（默认 `https://api.tavily.com`，`Authorization: Bearer`）。两者直接用 `fetch` 实现，不引入官方 SDK，便于用本地 HTTP 服务测试并减少依赖。搜索端点来自可信配置，可以是用户自建的内网 SearXNG，不受网页读取的地址限制；错误信息不包含 key。
- **网页读取**（`src/web/fetch.ts`）：使用 `node:http` / `node:https`，在连接时通过自定义 `lookup` 校验实际解析到的地址，避免先查 DNS 再连接之间被换成内网地址；IP 字面量单独校验。拒绝回环、私网、链路本地、运营商 NAT、保留与组播地址、云 metadata 地址、IPv4 映射或 NAT64 形式的上述地址。只允许 http/https，拒绝 URL 中带用户名密码及 `localhost` 类主机名。重定向手动处理并逐跳重新校验，最多 5 次；限制超时、响应字节数及内容类型（HTML、XHTML、纯文本）；支持 gzip/deflate/br 及按 `charset` 解码 GBK 等编码。不执行脚本、不发送 cookie。正文用 `@mozilla/readability` 配合 `linkedom` 抽取（两者在读取网页时才动态加载，不影响命令行启动），抽取失败时退回去掉脚本与样式后的纯文本，再按 `max_chars` 截断。未采用 `request-filtering-agent`：内置 `lookup` 已能在连接时校验，不需要额外依赖。
- **工具与会话**（`src/web/tools.ts`）：`WebSession` 保存本对话已获取的来源，按出现顺序编号为 `web:N`；搜索结果以摘要作为来源正文，读取网页后同一 URL 的来源正文替换为页面正文。工具结果为 JSON，带 `untrusted: true` 与提示语，正文放在 `content` 字段，不改变 system prompt，也不插入 user 消息，保持第 8.2 节不变式。
- **副作用工具门禁**：对话中只要有联网工具返回过内容（包括历史中的），`record_profile`、`record_learning`、`playbook_update` 等写入工具执行前必须经过审批（`ApprovalRequest` 新增 `after_web`），没有审批入口时拒绝。网页内容因此不能写入画像、learnings 或 playbook。轮次结束后的自动画像学习只读取用户原话，不受网页影响。
- **引用**：回答中外部资料写作 `[web:N]`，直接引用原文时用「摘句」[web:N]。`findWebCitations` 校验编号是否存在、摘句是否出现在该来源正文（忽略空白），并列出回答里出现但本对话未获取过的 URL。外部引用与互动证据 ID 分属不同命名空间，`findCitations` 不把 `web:N` 当作数据 ID。
- **残余风险**：开启后，被分析数据中的注入文字仍可能诱导模型把数据内容写进搜索词或 URL 发往外部；门禁只保护本地写入，不能完全阻止这种外传。因此默认关闭，并在 README 提示只对可公开处理的数据开启。
- **预算与缓存**：任务账本新增 `web` 计数：搜索次数、读取次数、读取字节数、缓存命中次数。每个任务（一轮对话、一次 ask）网络请求次数默认最多 8 次，达到上限后工具返回错误，不再发请求；缓存命中不计入次数上限。缓存位于项目 `.ugc-lens/web-cache/`，按搜索后端与查询、或 URL 作键，记录原获取时间与过期时间（默认 24 小时），命中时返回原获取时间；损坏的缓存条目按未命中处理，写入使用临时文件加改名。

### 2.8 场景手册与核心结论补查（roadmap 第 17 步）

第 17 步已实现。

- **场景手册**（`src/analysis/scenarios.ts`，手册位于 `playbook/scenarios/<id>.md`）：Markdown 格式，`# 标题`、`## 分析方向`、`## 规则` 三部分，方向与规则均为列表。`applyScenario` 返回新的 playbook 快照，把场景规则追加到共同规则末尾，版本号与指纹沿用原手册，原快照不变；报告另行标明场景名称与场景手册指纹，便于追溯。用户显式传入的关注点优先于场景方向，场景规则仍然生效。
- **补查**（`src/pipeline/recheck.ts`）：综合发现的输出新增可选字段 `recheck_queries`（每项最多 3 个关键词，语法同 `search_feedback`）。代码按关键词检索评论、回复与记录（不含弹幕和字幕），排除该发现已引用的 ID，按点赞排序；严格匹配的可核对原文少于 3 条时，补充“任一词出现”的结果并在报告中注明，严格命中排在前面；每项最多 8 条、每条最多 600 字、总计最多 30000 字符。一次模型调用 `submit_recheck` 对候选逐条给出 `contradicts` / `qualifies` / `supports` / `unrelated`；反例和限定必须带逐字摘句，代码拒绝不在该项候选中的 ID、不是原文子串的摘句和越界的发现编号。没有关键词或没有候选时不调用模型。
- **呈现**：报告在每项发现的“待验证事项”之后增加“补查”，写明关键词、检索命中数与核对条数，列出反例与限定；没有发现时写“这些关键词的检索范围内未发现反例或限定”，不扩大为“不存在”。补查失败时写明“补查未完成”及原因。
- **成本**：补查是一次额外的模型调用，计入任务账本、调用次数和报告用量；默认开启，`analyze --no-recheck` 或 API `recheck: false` 关闭。

### 2.9 宿主模型模式（roadmap 第 17.6 步）

- 目的：用户不配置 ugc-lens 的模型 key，也能在 Claude Code、Codex 等宿主里完成完整分析。需要模型判断的步骤交给宿主自己的模型，ugc-lens 只做确定性步骤；全程不读取模型配置，也不调用任何模型接口。
- 分工：

| 步骤 | 配置 key 的完整流水线 | 宿主模型模式 |
|---|---|---|
| 结构识别 | ugc-lens 模型 | 内置规则、缓存规则；都没有时宿主按 `host describe` 的结构摘要写规则，`host mapping` 校验并写缓存 |
| 统计、关键词、弹幕高峰、时间轴 | 代码 | 代码（`facts.md`，`renderFacts`） |
| 去重、压缩、抽样、分块 | 代码 | 代码，同一 `planChunks`；块内编号换回原 ID |
| 分块总结、合并、综合 | ugc-lens 模型 | 宿主按 `guide.md`（含当前 playbook 的总结与合并规则）阅读 `chunks/*.md` 写报告 |
| 逐条情感、主题归类、商业机会 | ugc-lens 模型分批提交 | `host label-export` 导出批次与同一份规则，宿主写 `answers/*.jsonl`，`host label-import` 用同一行格式、校验与汇总函数（`sentimentRow`/`sentimentStats`、`topicRow`/`summarizeTopics`、`businessRow`/`rankOpportunities`） |
| 核心结论补查 | ugc-lens 模型判断候选 | `host recheck` 复用 `collectRecheckCandidates` 给出未引用候选，宿主判断并在报告中引用 |
| 分析手册修改 | `playbook_update` 工具 | `host propose` 写待审修改，仍由用户 `playbook --apply` |
| 监听目录 | 支持 | 不支持：需要常驻模型 |
| 精确计数、原文回查 | 工具 | `host search` / `host get` |
| 引用校验 | 代码 | `host verify`：ID 存在，`"摘句" [ID]` 逐字出现在原文或分块显示文本中 |

- 入口为命令行 `ugc-lens host <describe|mapping|prepare|search|get|verify>`，JSON 输出，技能通过 shell 调用；`.ugc-lens/` 以当前目录为准。MCP 服务的数据工具在导入命中内置或缓存规则时同样不需要 key，暂不新增 MCP 工具。
- 内置规则（`src/ingest/presets.ts`）：缓存未命中后、请模型识别前尝试；要求试转换无错误、无遗漏数组且有导入内容，否则仍走原流程。`useCache: false`（强制重新识别）时跳过内置规则。首个内置规则为 media_crawl 的 B 站 `*_all.json`，路径有 BV 号用 BV 号，否则用目录名末尾的数字。
- 逐条标注（roadmap 第 17.7 步）：导出时按范围筛选、可用固定种子随机抽样，超长原文跳过不截断；导入时逐行校验，格式错误、批外、重复 ID 和商业摘句不是原文子串都记为错误，重复 ID 的两行都不采用；未标注的条目记为跳过。汇总口径与完整流水线相同，抽样时附 `scope_note`。
- 边界：数量来自 `search` 的真实匹配、逐条标注的汇总，或标明为估计；核验只证明引用可追溯，不评价解读。耗用的是宿主额度，数据很大时分块数随 `--chars` 增长，宿主应按清单逐块读完或在报告里写明未读范围。

## 3. Agent 循环

### 情感评分工具（第 14.5 步）

- `analyze_sentiment` 与数据查询工具共同提供给对话、ask 和 MCP。调用时由独立模型请求顺序处理小批原文（默认每批 40 条、最多 12000 字符），通过 function call 返回逐条 ID、情感分数（-1～1，无法判断为 null）和简短理由；支持按类型、内容 ID 和评价对象筛选。
- 代码校验分数、批内 ID、重复与遗漏，保留逐条结果。按固定阈值（大于 0.2 正面、小于 -0.2 负面，其余中性）汇总数量、比例和均值，并按内容类型分别统计。点赞不加权，不把情绪正负当作支持/反对立场，不把模型评分当作统计置信度。
- 工具返回汇总和少量引用示例，最终一轮由宿主模型解读。完整结果保存在 `.ugc-lens/sentiment/`；纯代码 API 返回完整结果，不自动写文件。批请求不携带其他批次历史，也不改变外层 Agent 的消息不变式。
- 默认独立 token 预算 30000（软上限）；失败、遗漏、过长和预算未处理的内容分别计数，不能归入中性。提供实际评估覆盖率、用量和停止原因，明确其分母是导入数据，不能外推成平台全量比例。
- 搜集端采样与分析端覆盖分开描述：平台回复计数与导入数只是数量对照，不据此判定搜集失败或样本无效。导出未携带采样设计时不推测置信度；只有问题依赖缺失的回复链、时间或字段时才说明相应限制。

### 第 15 步实现约定

- 分批语义分类使用共享执行器：独立请求、固定 system、ID 与参数校验、软 token 预算、失败和遗漏隔离。`analyze_topics` 可先用既有流水线发现主题，或接收明确的主题及纳入标准，再逐条多标签归类；每条记录等权，比例分母为成功归类条数，保留未归类、失败及跳过。主题与原文引用必须可核验，完整结果写本地 JSON。
- `analyze_business` 使用随包发布的商业手册，发现机会时只接收有原文摘句和 ID 的条目；机会必须包含假设、最小验证动作、投入及优先级，无证据不凑数。可用本地画像作为不可信背景，画像不能代替需求证据；不自动估算 ROI。
- `get_analysis_coverage` 和报告区分导入跳过、重复信号、实际送入成功总结块、失败块、预算跳过和未选择；重复只是数据特征，不是水军结论。总结块处理成功不等于逐条标签已核验，报告明确统计阶段；情感及主题工具另给逐条覆盖记录。
- `get_content_timeline` 按 content_id 隔离时间轴，代码对齐弹幕窗口与重叠字幕，返回真实时间和 ID；无字幕时不生成内容猜测。固定报告加入对应时间段的字幕引用。细分情感增加混合、反讽及评价对象字段，无法确定时保持 unknown，不将混合均值直接展示为中性。
- 本地关注点学习默认开启，从用户附带要求、主动追问或明确自述提取有直接引用的条目；只发文件、常规分析或寒暄不触发学习，既有关闭状态保留，持续保存至当前 profile 的 Markdown 文档；自动学习只读取本轮用户文本，不读取数据集或模型/工具结果。明确的“我…”自述可记录为 self_report，其他推断为 candidate；用户通过 CLI 修正的条目优先，不被模型覆盖。文档保留来源、作用域、时间和有限修订，可按全局或项目维护；自述是来源类型，不表示事实已经外部核实。
- `read_profile`、`record_profile` 在已开启的对话中提供，读取与任务相关条目；CLI 提供启停、查看、纠正、确认、删除、清空和导入选定历史文本。删除时保留不可逆摘要墓碑防止旧历史重新学习，清空同时停用。画像作为工具数据进入后续消息，system 不变。历史学习的额外用量单独报告，失败保留正常回答，核心 API 未传 memory 时不启用。

### 3.1 基本原理

Agent 的本质是一个 while 循环：

```
messages = [system, user]
loop:
    response = 调用模型(messages, tools)
    messages.push(response)
    if response 没有 tool_calls:
        结束，response.content 就是最终回答
    for each tool_call in response.tool_calls:
        result = 执行工具(tool_call.name, tool_call.arguments)
        messages.push({ role: "tool", tool_call_id, content: result })
    检查终止条件（步数、token、时间、取消）
```

要点：
- **模型不会执行任何东西**。它只返回“我想调用某个工具、参数是什么”，执行是我们的代码做的。
- **循环由工具调用驱动**。模型不再请求工具时，循环自然结束。
- **messages 就是 Agent 的全部记忆**。每轮都把完整历史发给模型。

### 3.2 终止条件

任何一条满足就停止，并在结果里写明停止原因：

| 条件 | 默认值 | 停止原因 |
|---|---|---|
| 模型不再请求工具 | - | `completed` |
| 最大循环步数 | 10 | `max_steps` |
| 累计 token 预算 | 100k | `token_budget` |
| 总耗时 | 5 分钟 | `timeout` |
| 用户取消（AbortSignal） | - | `aborted` |
| 连续工具错误 | 3 次 | `tool_errors` |

停在 `max_steps`、`token_budget`、`tool_errors` 时，做一次**收尾调用**，让模型基于已有信息回答，并说明哪些信息不足：

- 请求里仍然带上工具定义，但设置 `tool_choice: "none"`，模型只能用文字回答。部分提供商要求：历史里出现过工具调用时，请求必须带工具定义。
- 收尾提示区分运行限制和源数据质量：说明尚未完成的分析，不因预算、步数或工具错误停止就断言源数据缺失、采样无效。
- 收尾说明附加在**最后一条、还没发给模型的工具结果**末尾，不额外插入 user 消息（见第 8.2 节）。停止检查发生在工具执行之后、下一次调用模型之前，所以这条工具结果一定还没发出去。
- `timeout`、`aborted` 不做收尾调用：时间已经用完，或用户已经取消。

token 预算是**软上限**：每一步开始前检查累计用量，达到预算就不再开始新的步骤。已经开始的那次调用和收尾调用仍会计入，所以实际用量可能超过预算。历史越长，每次调用越贵，超出越多：第 6 步实测预算 3000，实际用了约 8800（第 2 步开始前累计约 1000，第 2 步本身约 3000，收尾调用约 5600）。
### 3.3 错误处理

- 工具执行出错**不抛异常中断循环**，而是把错误信息作为工具结果返回给模型，让它换参数重试或换方法。
- 模型返回的参数不是合法 JSON，或者不符合 schema：同样作为工具结果返回错误说明。不符合 schema 时提示“参数不正确”，和“执行失败”区分开（见 4.1）。
- 模型接口本身出错：在模型客户端里重试（`src/llm/retry.ts`），重试用完再让循环失败。
  - 重试：网络错误、单次请求超时、HTTP 408、429、5xx。不重试：400、401、402、403、404 等其他错误，重试多少次结果都一样。
  - 默认最多重试 3 次（配置项 `max_retries`）。等待时间按指数退避：1 秒、2 秒、4 秒……最多 10 秒，再随机减少最多 25%，避免多个请求同时重试。
  - 响应带 `retry-after-ms` 或 `Retry-After` 时按它等待；超过 60 秒则不照办，改用退避时间。
  - 调用方取消或运行总超时时立即停止，等待中的重试也会被打断，不再继续。
  - 每次重试前发出 `model_retry` 事件（第 3.5 节）。重试用完后，错误信息里注明已重试的次数。
  - 限流只做被动应对（收到 429 后等待重试），不主动控制请求速度。分析流水线需要并行调用模型时再做并发控制。
### 3.4 循环的输出

```ts
interface AgentRunResult {
  answer: string            // 最终回答
  stop_reason: 'completed' | 'max_steps' | 'token_budget' | 'timeout' | 'aborted' | 'tool_errors'
  steps: AgentStep[]        // 每一步的模型输出和工具调用，用于调试和展示
  usage: { input_tokens: number; output_tokens: number }
  duration_ms: number
}
```

`steps` 是调试和学习的关键：每次运行都能完整回看模型“想了什么、调了什么、拿到了什么”。

### 3.5 运行事件

循环和流水线在运行过程中发出事件，入口层（命令行、MCP、图形界面）订阅后各自展示：

```ts
type RunEvent =
  | { type: 'run_start'; run_id: string; kind: 'agent' | 'pipeline' }
  | { type: 'model_start'; run_id: string; step: number; final: boolean }   // final：收尾调用
  | { type: 'model_delta'; run_id: string; step: number; text: string }     // 流式输出时的增量文本
  | { type: 'model_end'; run_id: string; step: number; usage: Usage; tool_calls: number }
  | { type: 'model_retry'; run_id: string; step: number; attempt: number; delay_ms: number; reason: string }  // 模型接口重试前
  | { type: 'tool_start'; run_id: string; step: number; call_id: string; name: string; args: unknown }
  | { type: 'tool_end'; run_id: string; step: number; call_id: string; name: string; ok: boolean; duration_ms: number }
  | { type: 'pipeline_stage'; run_id: string; stage: string; progress?: number }
  | { type: 'run_end'; run_id: string; stop_reason: string; usage: Usage; duration_ms: number }
```

每个事件都带 `run_id`，同时有多个运行时（比如监听目录时并发分析），入口层也能区分。

核心只负责发出事件，不关心谁来显示。这样命令行打印进度和图形界面画进度条，用的是同一份数据。

## 4. 工具层（function call）

### 4.1 工具定义

两层定义：循环只认底层的 `AgentTool`；写工具时用 `defineTool`，参数用 Zod 描述。

```ts
// 循环使用的底层接口（src/tools/types.ts）
interface AgentTool {
  name: string                 // snake_case，如 search_feedback
  description: string          // 写给模型看：做什么、什么时候用、返回什么
  parameters: JsonSchema       // 发给模型的参数格式
  execute(args: Record<string, unknown>, ctx: ToolContext): Promise<string>
}

// 推荐写法（src/tools/define.ts）
const tool = defineTool({
  name: 'read_file',
  description: '…',
  parameters: z.object({ path: z.string(), offset: z.number().int().min(1).default(1) }),
  execute: async (args, ctx) => { /* args 的类型由 Zod 推导，已校验、已填默认值 */ },
})
```

- 参数用 Zod 定义，一份定义同时用于“告诉模型参数格式”（转成 JSON Schema）和“校验模型传回的参数”。
- 转换时去掉 `$schema` 和 `z.number().int()` 自动带上的安全整数边界；带默认值的字段不放进 `required`。JSON Schema 表达不了的类型（如 `z.date()`）在定义时就报错。
- `refine` 写的规则不会出现在 JSON Schema 里，模型只能从错误提示中得知。重要的约束要写进 `description` 或用 JSON Schema 能表达的写法（`enum`、`min`、`regex`）。
- 参数不合格时抛出 `ToolArgumentError`，循环返回“参数不正确”的提示：逐条列出参数名、原因、收到的值，并附上完整参数格式，方便模型修正。
- `description` 的质量直接决定模型会不会正确使用工具，要当作提示词来写。
- 工具结果统一转成字符串返回给模型，超过长度上限时截断，并注明“已截断，可用分页参数继续读取”。
### 4.2 工具清单（按实现顺序）

| 阶段 | 工具 | 作用 |
|---|---|---|
| 基础 | `read_file` / `write_file` / `run_command` | 读写本地文件、执行命令，验证调用链路和确认机制（见 4.3） |
| 基础 | `calculate` | 两个数的四则运算、乘方、取余，练习 `enum` 和数字参数 |
| 数据 | `list_datasets` | 列出已导入的数据集（见 4.4） |
| 数据 | `get_dataset_stats` | 内容信息、数量、回复搜集比例、时间和地域分布、高赞内容 |
| 数据 | `search_feedback` | 按关键词、类型、时间、点赞数、属地筛选互动内容，分页返回 |
| 数据 | `get_feedback` | 按 ID 读取全文及上下文（上一级、回复） |
| 报告 | `list_reports` / `get_report` | 读取已生成的报告 |
| 联网 | `web_search` / `web_fetch` | 默认关闭；搜索网页、读取网页正文，结果为不可信外部资料（见 2.7） |
| 第二版 | `collect` | 通过数据源接口补充搜集 |

### 4.3 基础工具与确认

`src/tools/builtin/` 提供三个通用工具，用来练习 function call，也让 `ask` 能直接查看本地文件：

| 工具 | 参数 | 行为 | 需要确认 |
|---|---|---|---|
| `read_file` | `path`、`offset`、`limit` | 带行号返回文本，默认每次 500 行、最多 1 万字符，结果末尾提示下一段的 `offset`；拒绝目录、二进制和超过 10 MB 的文件 | 不需要 |
| `write_file` | `path`、`content` | 写入完整内容，自动创建上级目录 | 覆盖已有文件时需要 |
| `calculate` | `operation`、`a`、`b` | 精确计算，除以 0 和溢出时报错 | 不需要 |
| `run_command` | `command` | 用 shell 在工作目录执行，合并 stdout 和 stderr，返回退出码；30 秒超时，输出超过 1 万字符时保留开头和结尾 | 只读白名单以外的命令需要 |

规则：

- **路径不限制范围**。相对路径以工作目录（`runAgent` 的 `cwd`，默认 `process.cwd()`）为基准，支持 `~`。
- **确认由入口层提供**。工具通过 `ctx.approve(request)` 请求确认，命令行在终端里询问 y/N，代码调用方传入自己的函数。没有提供确认函数时**一律拒绝**。用户拒绝时工具返回错误，交给模型换个办法。
- **只读白名单偏保守**（`command_policy.ts`）：命令名在白名单内（`ls`、`cat`、`rg`、`git status` 等），不含重定向、`;`、`&&`、`$`、反引号等字符，也不带 `find -exec`、`sort -o` 这类会写文件或执行程序的参数，才直接执行。管道只允许连接白名单命令。判断不了的写法一律需要确认。
- **子进程拿不到模型 key**：执行命令时去掉所有以 `_API_KEY` 结尾的环境变量。
- 超时或取消时结束整个进程组，避免命令留下后台子进程。

### 4.4 数据工具与追问

`src/tools/data/` 的四个工具让模型按需查询数据集，数据本身留在本机内存里，不整个塞进上下文。全部只读，不需要确认。

| 工具 | 参数 | 返回 |
|---|---|---|
| `list_datasets` | 无 | 每个数据集的 ID、平台、文件名、标题、条数 |
| `get_dataset_stats` | `dataset_id` | 内容信息（标题、平台数据、平台摘要）、各类条数、回复搜集比例、时间范围、IP 属地、点赞前 5 的评论 |
| `search_feedback` | `dataset_id`、`query`、`kinds`、`content_id`、`parent_id`、`min_likes`、`location`、`since`、`until`、`sort`、`offset`、`limit` | 每行一条，正文截到 150 字；末尾写明总数和下一页的 `offset` |
| `get_feedback` | `dataset_id`、`ids`（最多 10 个）、`reply_offset`、`reply_limit` | 全文（最多 2000 字）、上一级、按时间排列的回复（可分页） |

规则：

- **每条结果以 `[ID]` 开头**，格式固定：`[1003] 评论 赞94 回复3 2024-10-22 浙江 用户3：正文…（全文 165 字）`。模型回答时用同样的 `[ID]` 引用，程序据此核对。原文里自带的方括号（B 站表情 `[干杯]` 等）不是 ID，被模型连同原文引用时不算编造；Markdown 链接也不算。
- **长度控制**：每次结果最多 8000 字符（`maxOutputChars` 可改），按整行截断，并按实际显示的条数给出下一页的 `offset`；截断的正文注明全文长度，提示用 `get_feedback` 查看。
- **`dataset_id` 可省略**：只有一个数据集时自动使用它；有多个时报错并列出可用 ID。
- **关键词规则**：空格分隔的词都要出现，`|` 表示任意一个，不区分大小写。不做分词和同义词，靠模型多换几个词查。
- **说明样本不完整**：概况里写明“已采集主评论下标注的回复数合计 N 条，本次导入 M 条；不代表全视频回复覆盖率”；`get_feedback` 对没搜集到回复的条目单独说明。
- 查询逻辑在 `src/dataset/query.ts`（`searchFeedback`、`getFeedback`、`getReplies`、`findCitations`），不依赖工具层，第 9 步流水线直接调用。

`src/ask/` 的 `askDataset` 是追问入口：固定 system prompt（要求先看概况、用 `[ID]` 引用、说明多少条支持、不足时直说）+ 数据工具 + Agent 循环，最多 12 步。返回回答、运行记录和引用核对结果（`citations.valid` / `citations.invalid`）。连续追问时把上一轮的 `run.messages` 作为 `history` 传入。

## 5. 统一数据格式与导入

所有数据文件都先转换成统一格式，后续步骤只认这一种格式。**核心不认识任何特定软件的文件格式**：文件结构由模型识别，转换由代码完成（5.2 节）。

```ts
/** 平台名，模型根据文件内容判断：bilibili、douyin、xhs、zhihu、youtube、weibo、kuaishou，判断不了时为 unknown */
type Platform = string

/** 一条用户互动内容 */
interface FeedbackItem {
  id: string                 // 数据集内唯一：文件里有 ID 就用原始 ID，没有就生成 `${kind}-${序号}`
  platform: Platform
  kind: 'comment' | 'reply' | 'danmaku' | 'answer' | 'record'   // answer：知乎回答这类“对内容的长回应”
  content_id: string         // 所属视频、笔记或问题，对应 ContentInfo.id
  parent_id?: string         // 上一级：回复 → 评论；知乎评论 → 回答
  text: string               // 原文，不做清洗
  author?: { id?: string; name?: string; gender?: string; location?: string }   // location：IP 属地，导入时去掉“IP属地：”前缀
  likes?: number
  reply_count?: number       // 平台显示的回复总数，可能大于实际搜集到的数量
  created_at?: string        // ISO 8601
  video_time_sec?: number    // 弹幕在视频中的时间点
  danmaku_mode?: string      // 滚动、顶部、底部
}

/** 被评论的对象：视频、笔记、问题 */
interface ContentInfo {
  id: string                 // 文件里有 ID 就用原始 ID，否则可从文件路径中取（id_from_path），都没有时生成 `content-${序号}`
  platform: Platform
  title?: string             // 只有评论、没有内容详情的文件（如 MediaCrawler 的 *_comments_*.json）没有标题
  url?: string
  author?: string
  description?: string
  published_at?: string      // ISO 8601
  stats?: Record<string, number>   // 平台显示的播放、点赞、评论数等
  summary?: string           // 平台提供的内容摘要（如 B 站 AI 总结）
  transcript?: { start_sec: number; end_sec: number; text: string }[]   // 字幕
}

interface Dataset {
  id: string                 // 由文件绝对路径计算，同一文件每次导入得到相同 ID
  platform: Platform
  file_path: string
  contents: ContentInfo[]
  items: FeedbackItem[]
  imported_at: string
  mapping: { fingerprint: string; from_cache: boolean }   // 用了哪份映射规则（5.3 节）
  report: ImportReport       // 试转换报告：每个集合导入多少条、各字段命中率、警告
}
```

转换规则：

- **原文不改**。“回复 @某人 :”这类前缀保留在 `text` 里，清洗留给分析步骤决定。模型只决定“哪个字段是什么”，从不经手原文。
- **数字和时间由代码统一**，模型不用关心单位：
  - 数量：数字、数字字符串、`"1,234"`、`"1.2万"`、`"3w"`、`"10+"` 都能识别。
  - 时间：数字小于 1e11 视为秒，否则视为毫秒；字符串先当数字处理，否则用 `Date.parse`。
  - 视频内时间点：秒数，或 `"01:23"`、`"00:01:23"`。
- **区分平台显示的数量和实际搜集到的数量**。例如 B 站评论的 `replyCount` 是平台显示的回复数，实际只搜集到其中一部分。统计时两个数都给出，分析时不能把搜集到的数量当成全部。
- 支持的文件格式与读取边界见第 5.2.1 节，单文件最大 100 MB。

### 5.1 结构摘要与结构指纹

模型看不到整个文件，只看结构摘要（`src/ingest/shape.ts`）：

```
$.video_comments  array  长度 3
$.video_comments[]  object
$.video_comments[].content  string  例："直接3月或者9月去国开报名，报名都是要线下…"
$.video_comments[].time  number  例：1729594533000
$.video_comments[].replyList  array  长度 0~2
```

- 每个数组最多抽样 50 个元素（均匀抽取），合并它们的字段，避免只看第一条漏掉可选字段。
- 示例值截断到 40 个字符；摘要最多 300 行，超出时注明。
- **结构指纹**：所有“路径 + 类型”排序后取 sha256 前 16 位。不含示例值和数组长度，所以同一软件导出的不同文件通常得到同一个指纹。空数组没有元素结构、字段有时为 null，都会让指纹不同，所以指纹对不上时还会用其他规则试转换（5.3 节）。

### 5.2 映射规则

模型通过工具 `submit_mapping` 提交映射规则，参数格式用 Zod 定义（`src/ingest/mapping.ts`）。例：B 站 `bilibili_all.json`

```json
{
  "platform": "bilibili",
  "content": {
    "path": "$.video_info",
    "id_from_path": "(BV[0-9A-Za-z]{10})",
    "url_template": "https://www.bilibili.com/video/{id}",
    "fields": { "title": "title", "author": "owner", "published_at": "pubdate", "summary": "$.video_ai_summary.summary" },
    "stats": { "views": "view", "likes": "like" },
    "transcript": { "path": "$.video_zimu", "start": "from", "end": "to", "text": "content" }
  },
  "collections": [
    {
      "kind": "comment",
      "path": "$.video_comments",
      "fields": { "id": "rpid", "text": "content", "created_at": "time", "likes": "like", "author_name": "author" },
      "children": [{ "kind": "reply", "path": "replyList", "recursive": true }]
    },
    { "kind": "danmaku", "path": "$.video_danmus", "fields": { "text": "content", "video_time": "time", "danmaku_mode": "type" } }
  ]
}
```

路径写法：

- 绝对路径以 `$` 开头，`.` 分隔字段，`[]` 表示展开数组：`$.answers[].comments`。
- 字段路径相对于当前元素，只用 `.`：`user_info.nickname`。也可以写 `$` 开头的绝对路径，用于内容信息分散在文件多处的情况（如上例的 `summary`）。字段名本身含 `.` 的情况第一版不支持。

规则含义：

- `content`：被评论的对象。`path` 指向一个对象，或一个数组（每个元素是一个内容）。可选。
  - `id_from_path`：文件里没有内容 ID 时，用正则从文件路径中取第一个捕获组。
  - `url_template`：文件里没有链接时，用内容 ID 拼出链接，`{id}` 会被替换。
- `collections`：互动内容的集合，每个集合指定 `kind`、数组路径和字段。
  - `children`：嵌套在元素里的下一级（最多两层）。写了 `fields` 就完全按它来；不写时沿用上一级的规则，上一级有而这一级没有的字段（如回复没有 `reply_count`）只警告并忽略。`recursive: true` 表示同名字段在更深层重复出现（回复的回复）。下一级的 `parent_id` 自动指向上一级。
  - 扁平文件（所有评论在一个数组里）用 `fields.parent_id` 和 `fields.content_id` 表示关系。`parent_id` 为空、`0` 或 `"0"` 视为一级评论；有上一级的 `comment` 自动记为 `reply`。
- 互动内容归属哪个内容：
  1. 有 `fields.content_id` 就用它；文件里没有这个内容的详情时，自动生成只有 ID 的内容。
  2. 集合路径写在内容数组下面（内容 `$.notes`，评论 `$.notes[].comments`）时，属于所在的内容。
  3. 文件只有一个内容时属于它；没有 `content` 规则时生成一个内容。
  4. 以上都不满足（多个内容但无法对应）时，规则不通过。

### 5.2.1 通用文件读取（roadmap 第 9.5、14 步）

- 所有入口共用 `loadDataset`。读取上限仍为 100 MB，支持取消；按扩展名选择解析器。支持 UTF-8（可含 BOM）和带 BOM 的 UTF-16 LE/BE，拒绝非法编码和二进制内容。
- `.json` 保留原有流程；`.jsonl` / `.ndjson` 每个非空行必须是 JSON 对象或字符串，对象组成数组供现有映射推断，字符串转为带来源行 ID 的通用记录。混合对象和字符串时要求用户统一结构，不默默丢弃。
- `.csv` / `.tsv` 首个非空记录是表头，处理引号、双引号转义和引号内换行；CSV 支持逗号和分号分隔，TSV 使用制表符。空表头、重复表头、列数不匹配和未闭合引号明确报错。所有单元格保持字符串，防止 ID、日期、前导零被改写。内部列键为 column_1 等，另附原始表头映射（表头参与缓存指纹，不跨表头复用），让含点号、空格、中文的表头也可映射；每行带稳定来源行 ID。模型识别列用途，规则复用原有缓存。
- `.txt` / `.log` 按非空物理行生成记录，`.md` / `.markdown` 按空行分隔段落，保留段内换行；空文件报错。纯文本和全字符串 JSON 数组不需要模型识别格式，也不写映射缓存。
- 通用记录不套用评论的短内容过滤和 500 字截断。单条长记录超过分块软上限时独立成块，仍受总字数预算限制；预算放不下的记录不截断伪装为全文，报告覆盖率反映未纳入的记录。
- 新增 `record` 类型，适用于问卷、评价、工单、访谈等通用记录；未知来源平台写 unknown。统计、查询、分块、提示词和报告支持通用名称，原有 UGC 行为保持兼容。读取结果保留输入格式；内置映射单独标记，CLI 不把它描述成模型识别。
- 监听默认保持 `*_all.json`，避免扩大默认分析范围；用户可用 `--pattern` 选择上述格式。格式解析只读，不执行单元格公式或文本中的命令。

### 5.3 推断、校验与缓存

```
读文件 → 按格式解析 → 内置纯文本映射 / 结构摘要 + 指纹
  ├─ 同一指纹被拒绝过 → 报错（没有互动内容）
  ├─ 同一指纹的规则逐条试转换，没有错误 → 直接使用
  ├─ 其他指纹的规则逐条试转换，没有错误、也没有遗漏的数组 → 直接使用
  └─ 都不行，调用模型（Agent 循环，工具 submit_mapping / reject_file）
       submit_mapping → Zod 校验参数 → 试转换全部数据
         ├─ 有错误：作为工具结果交给模型，模型改正后重新提交
         └─ 通过：追加到这个指纹的缓存，返回 Dataset
       reject_file → 文件里没有互动内容（如搜索结果列表），记入缓存，报错说明原因
```

- 模型提交的规则按严格标准试转换，以下情况算错误：
  - 路径找不到数组；集合路径以 `[]` 结尾（指向了元素而不是数组）。
  - 某个集合一条都没导入，或超过一半元素取不到 `text`。
  - 某个字段的路径在所有元素上都不存在（多半是写错了）。
  - 有 `content` 规则却没有 ID 来源（`fields.id` 或 `id_from_path`），或 `id_from_path` 不匹配文件路径。
  - ID 相同但正文不同；多个内容无法对应。
- 只警告不出错：
  - 字段命中率低于 100%，或路径存在但值都为空（如 AI 总结为空字符串）。
  - `parent_id` 指向不存在的条目。
  - ID、正文、所属内容都相同的重复条目（同一条被搜集了两次），去掉重复的。
  - 有元素是对象、至少 5 个元素的数组没有被任何规则使用，提醒模型是否漏掉了弹幕之类的集合。内容对象和内容字段所在对象（如 `$.video_ai_summary`）里的数组不算。
- 缓存规则用在新文件上时放宽：除 `text`、`id` 外，字段路径不存在只警告。规则已经在别的文件上验证过，新文件缺少可选数据（如没有 AI 总结）很常见。
- 一个指纹可以有多条规则：结构相同，但有的文件路径里有 BV 号、有的没有，需要不同的 `id_from_path`。
- 复用第 3～6 步的机制：参数错误提示（4.1 节）、连续出错 3 次停止、重试。最多 6 步。
- 映射规则的对象都是严格模式：模型把字段写错位置（如 `title` 没放进 `fields`）时报错，不会被悄悄丢掉。
- 缓存放在 `.ugc-lens/mappings/<指纹>.json`，可以手动查看、修改或删除。内容为规则本身、来源文件名和生成时间。并行导入同一指纹的文件时，后写入的可能覆盖先写入的规则，最多多调用一次模型。
- 发给模型的结构摘要里有示例值，可能包含用户名等原文片段。后续分析本来就要把原文发给模型，这里不额外处理。
- 已知限制：超过 2^53 的数字 ID 在 `JSON.parse` 时会丢失精度，这类 ID 通常以字符串保存，暂不处理。
## 6. 分析流水线（固定步骤）

```
1. 导入        识别文件结构，按映射规则转成 Dataset（第 5 节）
2. 统计        纯代码：数量、分布、高赞、关键词
3. 分块总结     评论按数量分块，并行调用模型，每块提交观点 + 纳入标准 + 原文引用（6.3）
4. 合并        把各块观点合并、精炼成最多两层的主题（6.4）
5. 引用校验     纯代码：ID 存在、属于该块、摘句是原文子串；统计支持条数（6.5）
6. 写报告      输出 Markdown / HTML，附运行信息（耗时、调用次数、token）
7. 复盘        记录本次问题到 learnings.md
```

### 6.1 纯代码分析（`src/analysis/`）

模型之前先用代码把能算的都算出来：结果稳定、不花 token，也给模型的总结提供“有多少条”的硬数据。词频、弹幕时间轴、停用词沿用 media_crawl 的做法，另外加入几个文本挖掘里常用的算法：

| 功能 | 做法 | 来源 |
|---|---|---|
| 文本归一化、去重键 | NFKC 全角转半角，去掉“回复 @某人 :”前缀、链接、标点；连续超过 3 个相同的字压成 3 个 | — |
| 新词发现 | 统计 1～4 字片段，凝固度（片段与拆开后两部分的点互信息，取最小）≥ 5，自由度（左右邻字信息熵的较小值）≥ 1.5；短词几乎总在长词里出现时只留长词 | Matrix67《互联网时代的社会语言学》 |
| 分词 | `Intl.Segmenter`（Node 内置），新词发现的结果作为词典保护不被拆开；停用词和“好的”“很大”这类不成词的组合去掉 | media_crawl 的分词与停用词 |
| 关键词 | 文档频率：一条内容里出现多次只算一次，避免刷屏的内容占比过高 | media_crawl 的词频 |
| 区分度 | 带先验的对数几率比（z 分数），找出一部分内容（弹幕高峰、某个主题）相对其余内容特有的词 | Monroe 等 2008，“Fightin' Words” |
| 弹幕去重 | 按去重键合并，记重复次数，引用第一条的 ID | — |
| 弹幕高峰 | 时间轴分约 150 段（每段 5～60 秒），用中位数和 MAD 算稳健 z 分数，≥ 3.5 为高峰，相邻段合并 | Iglewicz & Hoaglin 修正 z 分数 |

没有采用的：

- **情感分类模型**（media_crawl 用 Transformers.js 跑 distilbert）：要下载模型、引入较重的依赖，中文网络用语上效果一般。态度由分块总结时的模型判断。
- **CES 互动评分和刷量检测**：阈值是按平台和播放量分档写的经验值，第 9 步报告里先给出互动率等原始比例，阈值规则以后放进 playbook。
- **向量聚类**：需要额外的向量模型接口，各家提供商差异大。第一版靠模型在分块总结里归纳主题。

新词发现的阈值是在真实 B 站数据（几千到十万条）上调的，语料很小时（几十条）凝固度普遍偏低，大多发现不了新词，这时分词只靠 `Intl.Segmenter`。

### 6.2 分块（`src/pipeline/chunk.ts`）

- **按串分块**：一级内容（评论、回答，以及上一级不在数据里的回复）和它下面所有层级的回复放在同一块，不拆开。每串最多 20 条回复，点赞多的在前。单串超过块上限时从后往前去掉回复。
- **复读分组**：仅同内容、同类型与相同父关系且没有回复的一级内容可分组，保留各成员 ID、原文与作者信息；有回复的串独立保留。大型重复组恢复为可装块的独立单元，仍受总字数抽样约束，不再承诺数万条压成一行且保留完整证据。
- **刷屏压缩**：连续 8 个以上相同字符显示为 `666…（6×215）`，只影响发给模型的文字，原文不变。
- **热度**：`log(1+赞) + 0.5·log(1+回复数)`，复读合并的再加 `0.5·log(1+重复数)`。取对数是为了不让一条爆款压过所有内容。
- **预算与抽样**：评论部分默认最多 8 万字符，每块最多 1.2 万字符（约 7 块，DeepSeek 上约 5～6 万 token）。超出预算时，预算的 30% 按热度直接保留，其余随机抽样（固定种子，结果可复现），让冷门内容也有机会被看到。覆盖率（放进了多少条、是否抽样）写进报告。可以用参数调大或调小。
- **弹幕**：按重复次数取前 300 组，加上各高峰时段里重复最多的组，单独成块，每行带重复次数和首次出现的视频时间。
- **字幕**：独立于弹幕分块，保留时间与内容归属，使用同一证据引用校验和原文回查；导入及实际分析覆盖按段数单独记录。
- **低信息内容不交给模型**：去掉表情和标点后不超过 3 个字、没有点赞、没有回复、也没有复读的内容（如“哈哈”“[笑哭]”），只由代码计数写进报告。
- **发给模型的行格式**（省 token）：
  - 每块内用短编号 `[1]`、`[2]`……代替原 ID，代码按块记下编号和原 ID 的对应关系。B 站 ID 有十几位，每行都带一个，换成短编号能省不少。
  - 保留点赞、日期、IP 属地、用户名：地区和时间本身就是要分析的信息。回复携带直接父 ID、根 ID 和内容归属；`↳` 缩进只表示它是一条回复，不表示直接回复上一行。
  - 保留正文前的“回复 @某人 :”；低信息过滤不删除其他回复所指向的父节点。
  - 截断时不把 emoji 拆成两半；客户端发送前也会把数据里本来就有的半个代理对换成 U+FFFD。半个字符会让 DeepSeek 无法解析请求体（真实数据上遇到过）。
  - 例：`[3] 赞94 2024-10-22 浙江 用户3：正文…（同样 +19）`，回复是 `  ↳[4] 赞2 … {parent=原ID root=根ID content=内容ID}`，弹幕是 `[9] ×5 00:10 正文`。

### 6.3 分块总结（`src/pipeline/summarize.ts`）

做法参考 Jigsaw sensemaking-tools、TopicGPT、LLooM：先在每块里各自找观点（发散），再统一合并（收敛）；每条观点都要有原文引用。原则是**代码能做的都由代码做，模型只读最少的文字、只写最短的输出**。

- **每块只调用一次模型**：不走 Agent 循环，直接调用模型，`tool_choice` 指定 `submit_findings`。走循环的话，工具结果返回后还要再调用一次让模型说“完成”。
- **关闭思考模式**：思考内容按输出 token 计费，DeepSeek 开着思考时还不接受指定工具（见 [providers.md](providers.md) 第 5 节）。提供商仍拒绝指定工具时（400 且错误里提到 tool_choice），改用 `auto` 重发，之后的块直接用 `auto`。
- **不重试格式错误**：参数逐条校验，合格的观点留下，不合格的丢掉并计数。再请模型改一次又要发一遍整块内容。
- **固定内容放前面**：说明、方向、数据集标题在 system prompt 里，各块完全相同；块内容放在 user 消息。这样各块请求的开头一致，能命中提供商的提示词缓存（DeepSeek 自动缓存，命中部分价格低得多），报告里写出命中的 token 数。
- 每条观点包含：
  - `direction`：分析方向的编号。默认四个：主要观点、吐槽点、正面评价、争议；调用时传入 `focus` 就只分析这些方向。
  - `title`：一句话结论，不超过 30 字。
  - `criteria`：纳入标准，用一句话说明什么样的内容算这条观点（来自 LLooM），不超过 30 字。合并时靠它判断两条观点是不是一回事。
  - `refs`：2～5 个块内编号。
  - `quotes`：只有被引用的内容超过 80 字时才写，照抄其中最能支持结论的一句（不超过 40 字）。短内容报告里由代码直接显示原文，不让模型重复输出。
  - `support`：这一块里大约有多少条内容支持（“同样 +N”和弹幕“×N”算进去）。
- 每块最多 8 条观点。
- 提示词不假设数据是“视频评论”，内容类型和标题从数据集里取，为第 9.5 步通用化做准备。
- 并发默认 4，可配置（sensemaking-tools 也是用并发上限控制限流）。单块失败按第 6 步的重试处理，重试用完记入结果，不中断整次分析。
- 开始前按字数估算 token（汉字约 0.9、其他字符约 0.4，按 DeepSeek 实测校准），供调用方提示。可以设 token 预算，已用量超过预算后不再开始新的块，跳过的块记入结果；预算仍是软上限（第 6 步）。

### 6.4 合并（`src/pipeline/merge.ts`）

- 把所有块的观点交给模型一次调用，`tool_choice` 指定 `submit_themes`。每个观点一行：`F编号 [方向编号] 结论｜纳入标准｜约 N 条`，不带原文和引用，输入很短。
- 按 TopicGPT 的“精炼”步骤：同一方向里意思相同的观点合并，最多两层（主题 → 子主题）。模型只输出主题标题和观点编号，支持条数、引用由代码从来源观点汇总，不让模型重复输出。
- 代码校验：编号必须存在、方向必须一致、每个观点只用一次。模型漏掉的观点各自单独成为主题，不会丢。
- 不调用模型的情况：所有观点来自同一块（块内不会重复），或者观点只有一条。合并调用失败时也退回到“每个观点单独成为主题”，报告照常生成。
- 支持太少的主题由代码去掉（默认少于 2 条），不交给模型判断。
- 不做 TopicGPT 的“逐条分配到主题”：要把每条内容再过一遍模型，调用次数和块数一样多，第一版不划算。

### 6.5 引用校验与支持条数（纯代码）

- 分块总结时（6.3）就校验每条引用：编号必须在这一块里（同时保证 ID 存在、属于该块）；摘句去掉空白后必须是原文的子串。然后把编号换回原 ID。
- 不合格的引用删掉；一条观点的引用全不合格时，这条观点删掉。丢掉了多少、为什么，记在返回结果里，不写进报告。
- 每个主题的支持条数是各来源观点的 `support` 相加（模型估计，报告里写“约”）。引用的内容有复读时，代码按去重键数出实际有多少条相同内容，标在引用后面。
- 不逐块增加 autorater 自检；报告在合并后用一次原文证据综合形成核心结论（第 6.6 节）。

### 6.6 报告（`src/pipeline/report.ts`）

- 在主题合并后增加一次证据综合（`pipeline/insights.ts`），使用已校验引用的原文，跨方向合并重复主题，省略无关互动，按重要性输出最多六项发现。每项包含发现、分组证据、反例/分歧、边界、意义和待验证事项；每个证据组均有独立引用，标题只能覆盖展示证据。综合属于模型解释，不是代码证明的语义事实。
- 综合阶段沿用任务预算和用量账本。仅接受输入证据集合内、原文摘句匹配的引用；不接受丢失某侧证据后仍保留结论的部分结果。失败、预算耗尽或无有效发现时明确说明，原主题作为未综合核对的附录，不冒充核心结论；成功综合后正文不再重复原主题，调用方仍可从返回值读取候选主题。
- 首页先显示核心结论和分析，再放统计附录。主题规模就地写明“模型估计涉及约……条，非逐条分类结果”。回复统计明确为已采集主评论标注回复数之和与本次导入回复数，不计算全视频回复覆盖率。
- 静态时间轴从全部窗口中按高峰、弹幕数选择关键窗口，再按内容及时间展示；完整时间轴在附录按时间展开，标注窗口内字幕和反应的摘录上限。

- 先只做 Markdown，保存到 `.ugc-lens/reports/<数据集 ID>-<时间>.md`。HTML 以后再加。
- **报告先结论后资料**：核心发现及论证、关键时间窗口在前，概况（数量、时间范围、覆盖了多少、是否抽样）、IP 属地、关键词、弹幕高峰、完整时间窗口和运行信息放附录。有块失败或被跳过时，只在运行信息里用一句话说明覆盖不完整，不列错误细节。
- 校验丢掉的内容、各块的错误原因留在 `analyzeDataset` 的返回结果里，给调用方和调试用。
- 引用显示：有摘句用摘句，否则由代码截取原文前 120 字。原始主题附录每个主题最多显示 3 条，点赞多的在前；核心发现按证据组分别显示引用，不能按点赞统一截断而丢失某一方。
- 概况、属地、关键词、高峰全部由代码生成，不经过模型。

### 6.7 监听目录（`src/watch/`、`src/store/tasks.ts`）

`ugc-lens watch <目录>`：目录里出现新的数据文件时，自动跑一遍 `analyzeDataset`。

- **哪些文件触发**：按文件名规则匹配，默认 `*_all.json`（搜集工具每个视频文件夹里有 comment、danmaku、summary、detail、all 好几个 JSON，只有 all 是完整的，全分析会重复花 token）。`--pattern` 可以改，多个规则用逗号分开，只支持 `*` 和 `?`。子目录也监听；`.` 开头的目录和 `node_modules` 跳过。
- **什么时候算写完**：用户的搜集工具在全部完成后才写 `*_all.json`，所以文件出现就算数据齐了。写入本身要时间，代码再等文件大小和修改时间连续不变（默认 2 秒）才开始。
- **怎么发现新文件**：`fs.watch`（递归）收到变化后扫描一次目录，另外每隔一段时间（默认 30 秒）定时扫描，补上 `fs.watch` 漏掉的事件。不用 chokidar：Node 22 的 `fs.watch` 在 macOS、Windows、Linux 都支持递归，加上定时扫描就够了，不多一个依赖。
- **已有文件**：启动时目录里已有的文件默认不分析，只分析启动之后新出现的；加 `--existing` 才分析已有的。
- **只分析一次**：任务按文件的绝对路径记录。已经分析过（不论成功失败）的文件，之后被覆盖或修改也跳过。失败的任务不自动重试，避免反复花 token；`--retry-failed` 启动时重试。
- **一次一个**：任务排队，同一时间只分析一个文件，控制 token 花费和接口并发。
- **任务状态**：存在 `<cwd>/.ugc-lens/tasks.json`，先写临时文件再改名，写到一半退出也不会损坏。状态：`pending`（排队）→ `running` → `done` / `failed`。记录文件路径、加入时间、开始和结束时间、报告路径、调用次数、token、失败原因。
- **重启续跑**：启动时把 `pending` 和 `running`（上次被中断）的任务重新排队，不受 `--existing` 影响。按 Ctrl+C 停止时取消正在进行的分析，任务保持 `running`，下次启动接着做。
- **进度**：`watchDirectory` 通过回调发出事件（开始监听、加入队列、开始、完成、失败、出错、停止），命令行把它们打印成一行一行的文字。分析本身的进度沿用 `analyzeDataset` 的 `onProgress`。
- 测试时可以注入分析函数，不调用模型。

## 7. 规则迭代：playbook 与 learnings（roadmap 第 13 步）

- 默认规则位于包内 `playbook/default.md`，按共同规则、追问、分块总结和合并分节，带正整数版本号，全文最多 4000 字符。协议格式、参数约束和引用校验仍由代码负责。
- CLI / MCP 按“项目 `.ugc-lens/playbook.md` > 全局 `~/.ugc-lens/playbook.md` > 包内默认”的顺序选择。`init` 首次复制全局副本，不覆盖已有内容；`ugc-lens playbook --init` 可将当前有效手册复制为项目副本。用户可以直接编辑规则，内容摘要会区分忘记修改版本号的手动更新。
- 一次完整分析只加载一份不可变快照，总结、合并和估算共用；报告记录版本号及内容摘要。一段连续问答和默认交互会话也固定使用开始时的快照，磁盘修改仅影响下一次分析或新对话。
- 核心代码 API 使用包内默认规则且不默认写经验文件，保持原有调用方无额外文件写入；传入 `memory: {cwd, homeDir?}` 启用项目规则与经验记录，或传入 `playbook` 快照。CLI、MCP 和目录监听默认启用对应工作目录的 memory。
- 运行经验写入项目 `.ugc-lens/learnings.md`，只追加。自动记录范围是完整分析和数据问答：数据集 ID、平台、规则版本与摘要、运行结果，以及代码可证实的问题（失败/跳过块、无效引用等）；不额外调用模型复盘，不记录 key、完整问题或完整回答，也不自动总结成跨数据集规律。
- `record_learning` 可记录带原文 ID 依据的候选经验，仅绑定当前数据集；`search_learnings` 按关键词和数据集分页返回原始记录。候选经验和历史结果不作为指令自动注入提示词。
- `playbook_update` 接收 add / patch / remove 操作，要求 patch / remove 的定位子串唯一；校验后只写项目待审文件 `.ugc-lens/playbook.pending.json`。`ugc-lens playbook` 显示有效规则和待审修改；用户运行 `ugc-lens playbook --apply <ID>` 才将其应用到项目副本，也可 `--reject <ID>` 放弃。原内容已变化时拒绝应用，避免覆盖人工修改。
- CLI 对话、问答和 MCP 暴露经验检索、候选记录及规则提案工具；模型不获得应用提案的工具。规则写入检查字数、疑似密钥、隐藏字符和指令注入。经验持久化失败显示警告，不让已生成的报告或回答丢失。
- 固定回归样本包括评论、回复链、弹幕及综合导入样本，由测试夹具提供：相同输入切换规则后检查模型实际收到的快照、输出与报告溯源信息，并覆盖旧对话冻结和待审规则不生效。

## 8. 记忆与上下文

参考 Hermes Agent 的记忆设计（MEMORY.md / USER.md、冻结快照、会话检索、上下文压缩）。现有实现分别记录分析经验和可选的本地用户画像，帮助模型根据当前使用者的目标、资源、偏好和人设提供建议。开源包不内置任何真实用户资料。

### 8.1 分层

| 层 | 内容 | 生命周期 | 怎么进入模型 |
|---|---|---|---|
| 运行上下文 | 一次运行的 `messages` | 单次运行 | 每次调用全部发送 |
| 运行记录 | `steps` 和事件，保存到 `.ugc-lens/runs/<run_id>.json` | 长期 | 不注入；用于调试、展示和检索 |
| playbook | 分析规则（第 7 节） | 长期，有字数上限 | 运行开始时注入 system prompt，运行中冻结 |
| learnings | 每次运行暴露的问题和反馈 | 长期，只追加 | 不注入；Agent 需要时用工具检索 |
| 用户画像（第 15 步） | 当前使用者的目标、偏好、技能资源、受众及自述人设 | 本地持续更新，可查看、纠正、删除和关闭 | 按任务选取相关条目，作为背景材料，通过工具读取；不作为系统指令 |
| 数据集与报告 | 统一格式的数据、生成的报告 | 长期 | 不注入；通过数据工具读取 |

#### 本地用户画像（第 15 步）

- AI 默认从 ugc-lens 用户主动附带的要求、追问和明确自述逐步提取与建议相关的信息，持续维护本机当前应用用户的 `~/.ugc-lens/user.md`；项目目标另行作用域隔离。用户不需要每次手写一份人设提示词；同一电脑上的不同应用用户或显式 profile 分开保存，不把“这台电脑”当作同一个人的身份凭据。
- 其他 Agent 的历史通过用户指定的文件或接入渠道导入，不自动扫描整台电脑。导入分析的评论、文章、访谈及工具输出属于分析材料，不能据此认定是操作者本人的经历或偏好。
- 用户明确自述的目标、资源与偏好可自动补充；AI 推断标为候选，不能当作已确认事实。条目记录来源会话或引用位置、记录与更新时间、适用范围及状态；对冲突和过期内容保留可追踪的修订，用户纠正优先。
- 通过专用工具读取、补充、修正和删除，实际落盘成功后才报告已记住；支持关闭自动学习、清空画像及删除来源关联。记录必要摘要，不复制整段历史，不存密钥或与任务无关的个人敏感信息。
- 画像作为生成建议时的背景，不替代当前用户要求或数据证据，不混入 playbook 的通用规则及 learnings 的分析经验。个性化建议说明相关假设，未确认信息用条件表达；更新通过工具结果进入后续上下文，不修改运行中固定的 system prompt。
- `UGC_LENS_PROFILE`（或代码 API 的 `memory.profile`）选择命名画像；默认文档为 `~/.ugc-lens/user.md`，命名画像为 `~/.ugc-lens/profiles/<name>/user.md`。项目条目按工作目录的绝对路径隔离。Markdown 的 JSON 数据块是唯一存储源；写入采用临时文件重命名和进程锁，冲突时返回可恢复错误，不覆盖其他进程的更新。
- 默认开启，但只从用户主动要求和追问中的关注信号增量学习，不持久化完整历史，不学习模型回复。只发文件或通用分析操作直接跳过，不额外调用模型；提问只证明关心某个维度，不能当成人物经历或身份。用户显式关闭后保持关闭。`profile --learn <TXT>` 可导入用户明确选择的、只含用户发言的历史文本，按空行分段。候选依据必须是本轮原文子串；显式材料、代码块不自动学习。来源存为发言摘要和直接引用，不将模型回复作为事实来源。

### 8.2 规则

1. **system prompt 在一次运行中不变**。运行开始时组装（基础指令 + playbook 快照），运行中不修改。运行中提出的 playbook 修改，经用户应用后，下次分析或新对话才生效。这样每次调用的前缀相同，能命中提供商的提示词缓存。
2. **不伪造消息、不改历史**。循环中不插入程序生成的 user 消息，不修改已经发给模型的消息。唯一的例外是以后的上下文压缩（8.3）。
3. **工具调用与结果严格对应**。带 `tool_calls` 的 assistant 消息后面，必须紧跟每个 `tool_call_id` 对应的 tool 消息，工具出错也要有结果。
4. **playbook 有字数上限**（默认 4000 字符）。写入超限时工具返回错误，附上当前用量、超出多少和现有条目，由 Agent 合并或删除旧条目后重试；不自动压缩。
5. **Agent 写入只能通过工具，用户可以手动编辑副本**。`playbook_update` 工具每次接收一个 `add` / `patch` / `remove` 操作，`patch` 和 `remove` 用唯一子串定位条目。写入先放进待审核区（`.ugc-lens/playbook.pending.json`），用户确认后才生效。模型口头说“已记录”不算数。
6. **写入前检查内容**。拒绝疑似密钥、隐藏的 Unicode 字符、类似“忽略之前的指令”的注入内容，因为 playbook 会进入 system prompt。
7. **检索返回原文**。检索 learnings 和运行记录时返回原文片段，不经过模型总结，避免丢失细节。

### 8.3 上下文长度

第一版不做上下文压缩，靠这两点控制长度：工具结果截断和分页（第 4.1 节）；`ask` 循环有步数上限。

以后需要时参考 Hermes 的做法：用到上下文窗口一定比例时，保留开头几条和最近若干条消息，中间部分用单独一次模型调用生成摘要。这是唯一允许改动历史的情况。

## 10. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript | 类型约束工具参数和数据格式 |
| 运行时 | Node.js ≥ 22.18（开发和运行都用 Node） | 以兼容为主；Bun 只用于安装依赖 |
| 模型接口 | OpenAI 兼容 Chat Completions，用户自选提供商 | 一个客户端覆盖国内外主流厂商和本地模型，见 [模型提供商](providers.md) |
| Agent 框架 | 不用，手写循环 | 便于学习和掌控细节，依赖少 |
| 参数校验 | Zod | 一份定义同时生成 JSON Schema 和做校验 |
| 本地状态 | JSON 文件 | 避免原生模块安装问题；数据量增长后再考虑 `node:sqlite` |
| 文件监听 | Node 自带 `fs.watch`（递归）+ 定时扫描 | 不多一个依赖；写完判定用文件大小连续不变（第 6.7 节） |
| MCP | 官方 TypeScript SDK | |
| 发布 | `tsc` 编译到 `dist/`，GitHub Actions + npm Trusted Publishing | 不额外引入打包工具；不存 npm token（第 2.2 节） |
| 依赖版本 | 全部固定精确版本，不使用 `^`、`~` | 避免不同时间安装得到不同版本；由 `bunfig.toml`（`exact = true`）和 `.npmrc`（`save-exact=true`）强制 |
