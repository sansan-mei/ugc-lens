## 改动内容

- 删除 media_crawl 专用的 B 站适配器和文件名白名单（`src/sources/`、`test/sources/`）。
- 新增 `src/ingest/`：
  - `shape.ts`：结构摘要（路径、类型、数组长度、示例值，数组均匀抽样）和结构指纹。
  - `mapping.ts`：映射规则的 Zod 定义，路径规则用 `regex` 表达，对象都是严格模式。
  - `apply.ts`：按规则转换全部数据，生成试转换报告（各集合导入数、字段命中率、错误、警告、遗漏的数组）。
  - `convert.ts`、`paths.ts`：数量、时间、视频时间点的转换，路径解析。
  - `infer.ts`：用 Agent 循环和两个工具（`submit_mapping`、`reject_file`）让模型推断规则，试转换错误作为工具结果交给模型。
  - `cache.ts`：规则缓存，`.ugc-lens/mappings/<指纹>.json`，一个指纹可以有多条规则。
  - `index.ts`：`loadDataset`（读文件 → 摘要 → 试缓存规则 → 调用模型 → 写缓存）、`ImportError`（带 `code`）。
- `src/dataset/types.ts`：`Platform` 改为字符串；`ContentInfo.title` 改为可选；`Dataset` 去掉 `source`，新增 `mapping`、`report`；新增 `ImportReport`、`CollectionReport`。
- 测试样本移到 `test/fixtures/bilibili/`；`test/helpers/fixtures.ts` 新增手写的 B 站映射规则，代替模型输出。
- `examples/07_dataset_stats.ts` 改为调用真实模型，支持 `--fresh`；`npm run smoke` 使用 `--fresh`。
- 文档：`docs/architecture.md` 第 5 节重写（5.1 结构摘要与指纹、5.2 映射规则、5.3 推断、校验与缓存），第 1、2、6、9、11 节相应修改；`docs/roadmap.md` 第 7 步重写，第 13 步改为“更多文件格式与发布”；README 更新 `npm run stats` 说明。

## 设计决定

- 核心不认识任何特定软件的文件格式。模型只输出“哪个字段是什么”的规则，转换由代码完成：一个文件只调用一两次模型，原文不经过模型，规则能校验、能缓存、人能看懂。
- 放弃“模型逐条转换”：大文件贵且慢，模型可能改写原文，破坏引用校验。
- 放弃“模型写转换代码”：要执行任意代码，有安全风险，也难验证。
- 规则通过工具提交，复用第 3～6 步的循环、参数校验、连续错误上限和重试；试转换报告就是给模型的反馈。
- 缓存先试同一指纹的规则，再试其他指纹的规则；其他指纹的规则要求没有错误、没有遗漏的数组。试转换本身就是安全检查。
- 缓存规则用在新文件上时放宽字段检查（`text`、`id` 除外），因为新文件缺少可选数据很常见；模型新提交的规则按严格标准检查，用来发现写错的路径。
- 第一版只支持 JSON，规则自动使用、不需要用户确认（用户选择）。

## 验证

- `npm run typecheck` 通过。
- `npm test`：148 个用例全部通过。
- `npm run smoke` 通过（示例 07 调用真实 DeepSeek，每次 1.4～3 万 token，取决于模型改了几次规则）。
- 真实数据（DeepSeek）：
  - 26 个 B 站 `bilibili_all.json` 按顺序导入：调用模型 2 次，其余复用缓存；3330 条评论、7306 条回复、33637 条弹幕，与之前手写适配器的结果一致。
  - 小红书 `all_xhs.json` 两个、知乎 `all_zhihu.json`、YouTube `youtube_all.json`、MediaCrawler 扁平评论文件（B 站、知乎、快手）都是第一次提交就通过。
  - MediaCrawler 的视频列表、笔记详情、用户列表文件被模型拒绝，理由正确。
- 没有验证：抖音、微博文件（本机没有样本）；超过 100 MB 的文件；并行导入同一结构的文件时的缓存竞争。
- 模型输出有随机性：同一批文件多次运行，调用模型的次数在 2～6 次之间（取决于模型写出的 `id_from_path` 能否覆盖其他文件的路径）。
