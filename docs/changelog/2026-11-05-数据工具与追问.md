## 设计决定

- 数据留在本机，模型通过工具按需查询。只把概况和查出来的几十条交给模型，3 万条弹幕的数据集也不会撑爆上下文。
- 长度控制分三层：每页最多 50 条、正文截到 150 字（注明全文长度）、整个结果最多 8000 字符（按整行截断）。截断时一定写明总数和下一页的 `offset`，避免模型误以为看到的就是全部。
- 每条结果以 `[ID]` 开头，回答也用 `[ID]` 引用，便于程序核对；原文里自带的方括号（如 B 站表情）不算引用。
- 关键词只做“全部出现 / 任意一个”的子串匹配，不做分词和同义词：规则简单、结果可预期，换词由模型完成。
- 只有一个数据集时 `dataset_id` 可省略，省掉模型先调用 `list_datasets` 的一步。
- 查询函数和工具分开：`query.ts` 返回数据，工具负责格式和长度；第 9 步流水线直接用查询函数。
- 数据集先放在内存里（`DatasetStore`），持久化等第 10 步监听目录时再做。
- 暂不做命令行的 `ask` 命令，入口放到 MCP / CLI 阶段；现在通过示例脚本和代码调用使用。

## 验证

- `npm run typecheck` 通过。
- `npm test`：179 个用例全部通过。
- `npm run smoke` 通过，其中示例 08 调用真实 DeepSeek。
- 真实模型（DeepSeek，测试样本 12 条）：
  - “这个视频的评论主要在吐槽什么？”：5 步、约 1.2 万 token，引用 12 个 ID 全部存在；回答主动说明样本只有 3 条评论、回复只搜集到 18%。
  - 追问“点赞最多的那条吐槽，下面的回复是怎么说的？”：沿用上一轮对话，2 步完成，引用 3 个 ID 全部存在。
  - “评论里有人提到价格吗？”：模型用 `价格|多少钱|收费|…` 一次查多个词，4 步完成；这次发现了 `[干杯]` 被误判为编造 ID 的问题，已修复并补测试。
- 没有验证：上万条的大数据集上的回答质量和 token 消耗；多个数据集同时追问。
