# 发版自动附带桌面安装包

- 日期：2026-11-15
- 关联步骤：roadmap 第 19.1 步第 4 项

## 改动内容

- `.github/workflows/desktop.yml`：增加 `workflow_call` 触发，可被其他工作流调用；更新顶部说明。
- `.github/workflows/release.yml`：
  - `publish` job 输出 `version` 和 `desktop`；`desktop` 由 `gh release view` 判断该版本的 Release 上是否已有 dmg。
  - 新增 `desktop` job，调用 `desktop.yml` 构建 macOS dmg 与 Windows 安装包。
  - 新增 `github-release` job，用 `actions/download-artifact@v8.0.2` 下载两个平台的产物，Release 不存在时 `gh release create`（附下载表、放行提示和自动生成的变更列表），已存在时 `gh release upload --clobber`。
- 新增 `test/scripts/release.test.ts`：桌面工作流可被调用；发版工作流的 job 依赖、触发条件、产物名与上传命令；所有工作流的 action 都固定到完整版本号。
- 文档：`docs/architecture.md` CI 一节与目录说明、`README.md` 发布说明、`docs/roadmap.md` 第 19.1 步（第 4 项与上次完成的 .ico 状态）。

## 设计决定

- 复用 `desktop.yml`，不在 `release.yml` 里复制一份打包步骤，避免两处不一致。
- 是否打包看 Release 上有没有 dmg，而不是看 npm 是否刚发布：npm 发布成功但打包失败时，手动重跑即可补上桌面包，不会重复发 npm。
- 不在 `desktop.yml` 的矩阵 job 里直接上传 Release：那样要把它的权限提升为可写，而它在普通推送和 PR 上也会运行。上传集中在 `release.yml`，只有发版时才有写权限。
- Release 不做草稿，打包完成后直接发布；npm 先于桌面包发布，桌面包失败不影响 npm。

## 验证

- TDD：先写 `test/scripts/release.test.ts`，确认两项因工作流未改而失败，再实现。
- `npm run typecheck` 通过；`npm test` 全部通过。
- 用 Ruby 解析两个工作流 YAML，结构正确；把上传步骤的脚本取出，用假的 `gh` 在本机跑了一遍，命令参数和 Release 说明符合预期。
- 没有在 GitHub Actions 上实际运行，需要下一次改版本号推送到 master 时确认（包括上一项改动里 Windows .ico 的打包）。
- 没有运行 `npm run smoke`：只改工作流，不涉及模型调用。
